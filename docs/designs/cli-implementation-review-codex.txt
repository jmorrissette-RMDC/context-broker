## Purpose and Scope

This document defines the requirements for the Context Engineering Architecture (CEA) -- the system responsible for compacting conversation context, extracting durable knowledge into vector and graph stores, and providing intelligent context enrichment for calling agents.

The CEA replaces the current per-message extraction pipeline with a compaction-time extraction model and moves context enrichment from the server to the client. It operates as two components of a single architecture:

- **CEAs (server-side):** A deterministic StateGraph flow within the Context Broker that runs at compaction time. Executes tiered summarization (tier 1 to tier 2 to tier 3), extracts durable facts and graph triples via Mem0, manages the memory store's integrity (deduplication, supersession, conflict detection), and sets immutable quality metadata on each extracted fact and graph relation.

# Context Engineering Architecture -- High-Level Design

**Version:** 1.0 **Date:** 2026-04-03 **Status:** Active

## 1. System Overview

The Context Engineering Architecture (CEA) is the knowledge management subsystem of the Context Broker. It extracts durable knowledge from conversations during compaction, stores it in vector and graph form, and provides intelligent retrieval and ranking for calling agents.

The CEA addresses a fundamental problem: the current per-message extraction pipeline extracts facts from small windows of raw messages without conversation context, producing decontextualized, redundant, low-quality knowledge. The CEA moves extraction to compaction time where the full conversation context is available, and introduces a feedback-driven quality model that learns from actual usage which knowledge is valuable.

The architecture follows a write-side / read-side separation:

- **CEAs (server-side)** runs at compaction time within the Context Broker. It is a deterministic StateGraph flow that produces structured extraction output, which a dispatch process writes to the stores.
- **CEAc (client-side)** runs at query time within the calling agent (e.g., the Imperator). It is an agentic StateGraph subgraph that searches, ranks, assembles enriched context, and records feedback.

Both components interact through a quality wrapper that sits around Mem0, adding quality metadata, feedback tracking, and enriched search results without modifying Mem0's internal pipeline.

These are the settled architecture decisions from 14 rounds of 3-CLI research. Full rationale is in GitHub issue #454 comments.

1. **Two-component architecture: CEAs + CEAc** â€” server-side deterministic flow + client-side agentic subgraph
2. **CEAs is a flow, CEAc is an agent** â€” CEAs produces JSON, dispatch writes to stores. CEAc has a tool loop.
3. **Four dimensions of memory quality** â€” usefulness (observed), durability (LLM prior, immutable), expiration (hard gate), trustworthiness (multiplier)
4. **Ranking: score = relevance x trustworthiness x memory_quality** â€” memory_quality blends durability + usefulness
5. **Facts are CR only** â€” immutable records, never updated, never deleted. All post-creation activity is feedback events.
6. **Append-only feedback event log** â€” replaces mutable counters. 6 event types: used, discarded, contradicted, superseded, invalidated, conflicted. All proportional except expiration.
7. **Quality wrapper around near-stock Mem0** â€” side-channel pattern is dead. Wrapper intercepts before add, after search. Fork reduced to elementId shim.
8. **Graph via Mem0-first** â€” re-enable _skip_graph, no reinvention of graph layer. Graph metadata in Postgres, not Neo4j edges.
9. **Client-side enrichment** â€” get_context returns tiers only. CEAc enriches via MCP tools. knowledge-enriched build type's server-side RAG is removed.
10. **MCP tools: add, search, list, feedback** â€” knowledge_get_context, knowledge_update, knowledge_delete removed. knowledge_search returns both vector + graph results.
11. **user_id = plain text string from message sender** â€” not conversation ownership, not context window participant
12. **Configurable extraction prompt templates** â€” two templates (vector facts, graph triples) in config directory
13. **Store-enriched single-pass extraction** â€” search existing facts before LLM call, inject as context, LLM labels NEW/DUPLICATE/SUPERSEDES/CONFLICTS
